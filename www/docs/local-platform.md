# The local platform

Run the whole thing (push, detect, build, publish, comment, update) with **no GitHub account, no network, and no
tunnel**. It is how the project is developed and demonstrated, and the fastest way to understand what NetFoundry
Preview does.

:::note Two different things are called "local"

They are independent, and you will usually use both.

| | What it does | Config |
|---|---|---|
| The local **platform** | Turns `git push` into a build | `local.enabled: true` |
| The local **exposer** | Serves previews at `/preview/<name>/` on the daemon's own listener | `exposer.kind: local` |

You can use the local platform with a zrok or ziti exposer, or GitHub with the local exposer.

:::

## It does not monitor git

There is no polling, no file watching, and nothing scanning a directory. A push is a webhook delivery, exactly as on
GitHub. Only the sender differs.

```
git push preview my-branch
        │
        ▼
  post-receive hook in the bare repo        ← generated by `docpreview sim init`
        │  curl -X POST /webhook/local
        ▼
  POST http://127.0.0.1:8471/webhook/local  ← the same ingress GitHub posts to
        │
        ▼
  clone → detect → build → publish → comment
```

The hook is the only simulated part. Everything after the webhook is the production path: the real queue, clone,
detector, builder, exposer and comment renderer.

That is the point. A mock that took a shortcut past the queue would not have caught the supersede races, and a fake
builder would not have caught the base-URL failures. Every bug listed in
[the design documents](https://github.com/openziti-test-kitchen/docpreview/tree/main/docs/design) was found through
this.

## Getting started

```powershell
# 1. A config with the local exposer. Then set local.enabled: true in it by hand.
docpreview init -exposer local

# 2. A bare repo that behaves like a GitHub repository.
docpreview sim init mydocs

# 3. Serve.
docpreview serve
```

`init` writes the `local:` section with `enabled: false`. Flip it to `true` before step 3, or the daemon ignores
every push.

`sim init` prints what to do next:

```text
Created C:\Users\you\.docpreview\repos\mydocs.git

Add it as a remote and push:

  git remote add preview "C:/Users/you/.docpreview/repos/mydocs.git"
  git push preview <branch>

Every push triggers a build and updates one comment.
Watch it at http://127.0.0.1:8471/pr
```

From the repository of any site that builds to static files:

```powershell
git remote add preview C:/Users/you/.docpreview/repos/mydocs.git
git push preview main                    # the base branch: no build
git checkout -b new-install-guide
# edit something under docs/
git commit -am "docs: rewrite the install steps"
git push preview new-install-guide       # this builds
```

Open `http://127.0.0.1:8471/` and watch it.

To seed a repository with content in one step, point `-seed` at an existing checkout:

```powershell
docpreview sim init mydocs -seed .\www
```

## What the hook does

`sim init` writes `hooks/post-receive` into the bare repository. It is a POSIX shell script you can read and edit:

```sh
#!/bin/sh
# Generated by 'docpreview sim init'. Turns a push into a webhook delivery.
set -e

WEBHOOK="http://127.0.0.1:8471/webhook/local"
REPO="$(basename "$(pwd)" .git)"
BASE="main"

while read -r _old new ref; do
  branch="${ref#refs/heads/}"

  # Pushing the base branch is not a pull request.
  [ "$branch" = "$BASE" ] && continue

  # A deleted branch closes its "pull request".
  if [ "$new" = "0000000000000000000000000000000000000000" ]; then
    action=closed
    new=""
  else
    action=synchronize
  fi

  # A stable number per branch, so repeated pushes update one comment instead
  # of opening a new one each time. cksum is in every POSIX environment;
  # collisions across branches are possible and harmless here.
  number="$(printf '%s' "$branch" | cksum | cut -d' ' -f1)"
  number=$((number % 9000 + 1000))

  printf 'docpreview: %s %s -> %s\n' "$action" "$branch" "$WEBHOOK" >&2

  curl -sS -X POST "$WEBHOOK" \
    -H 'Content-Type: application/json' \
    -d "{\"action\":\"$action\",\"repo\":\"$REPO\",\"number\":$number,\"branch\":\"$branch\",\"sha\":\"$new\",\"base\":\"$BASE\"}" \
    >&2 || printf 'docpreview: webhook unreachable — is the daemon running?\n' >&2
  printf '\n' >&2
done
```

Three decisions behind it:

- **The base branch is not a pull request.** Pushing `main` does nothing, which matches GitHub: a preview belongs to
  a branch under review.
- **The pull request number is `cksum` of the branch name**, so pushing the same branch twenty times updates one
  comment instead of opening twenty.
- **Deleting a branch closes it.** `git push preview --delete my-branch` tears the preview down, which is how you
  exercise the teardown path.

A push still succeeds when the daemon is down. The hook prints that the webhook was unreachable and carries on.

## Where the comment goes

There is no pull request to comment on, so the same `Report` is rendered as a page:

```
http://127.0.0.1:8471/pr              every simulated pull request
```

Watching that page update in place, through queued, building and ready with the revision counter climbing, is the
demonstration. The renderer is the one that produces the GitHub comment.

## Curl the webhook directly

The hook is a convenience. Nothing stops you posting the payload yourself, which is the quickest way to exercise a
state transition without a git operation:

```powershell
$body = @{
  action = 'synchronize'
  repo   = 'mydocs'
  number = 1234
  branch = 'new-install-guide'
  sha    = (git rev-parse HEAD)
  base   = 'main'
} | ConvertTo-Json

Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8471/webhook/local `
  -ContentType application/json -Body $body
```

The repository must exist under `local.repos_dir` and the SHA must be present in it, because the clone is real.

## Configuration

```yaml
local:
  enabled: true
  repos_dir: "C:\\Users\\you\\.docpreview\\repos"
  default_base: "main"
  webhook_secret: ""
```

| Field | |
|---|---|
| `enabled` | Turns the local platform on. The `/webhook/local` route always exists, but deliveries are ignored unless this is set. |
| `repos_dir` | Where `sim init` creates bare repositories, and the only place pushes are accepted from. |
| `default_base` | The base branch when `sim init -base` is not given, and when an event names none. |
| `webhook_secret` | If set, `/webhook/local` requires the same HMAC-SHA256 signature GitHub sends. Blank means unauthenticated. |

## Security

:::danger The local webhook is unauthenticated by default

With no `webhook_secret`, anyone who can reach the port can trigger a build of any repository under `repos_dir`.

That is acceptable for a loopback development loop on repositories you created. It is **not** acceptable on a shared
address. Do not enable `local.enabled` on a daemon whose ingress is reachable by anyone you would not hand a shell
to. Setting `webhook_secret` closes the endpoint, but the generated hook does not sign its requests, so you then
post deliveries yourself.

:::

The payload is still validated. A repository name containing a path separator is rejected, and the name must resolve
to an existing bare repository inside `repos_dir`. A payload cannot make the daemon clone an arbitrary path.

## The demo harness

`demo/` in the repository is a worked example: four Docusaurus projects, real `yarn build`, running at the same time,
with a secret configured so redaction is visible in every log.

```powershell
cd demo
.\Build-Template.ps1     # scaffold the Docusaurus template (slow, once)
.\New-Projects.ps1       # four bare repos and working copies
.\Start-Demo.ps1         # serve, and open the dashboard
.\Send-Burst.ps1         # twelve builds at once
.\Start-KeepBusy.ps1     # a wave every 90 seconds, forever
```

One of the four branches fails on purpose, with an MDX file importing a component that does not exist, so the failure
path and the build log viewer have something to show.

`demo/README.md` has the rest.

## Limits

- **`cksum` collisions.** Two branch names can map to the same pull request number and share a comment. Rename one.
- **No review state.** There is no approve, no merge, no draft. Only push, delete-branch, and the states a build
  produces.
- **Changed files come from git, not a platform API.** `git diff --name-only base...head`, with three dots, gives the
  changes since the branch diverged, not the changes since the tip of base. The hosted clients ask the platform
  because a depth-1 clone lacks the history. Here the bare repository *is* the platform and has all of it. A first
  push with no merge base treats the whole tree as changed, which is what "opened" means.
